Game Jam #3 - Make sure to delegate 구현 설명

이번 게임잼의 목표는 지금까지 제작한 Component를 실제 게임 규칙에 연결하고, 게임 로직을 가능한 한 Lua 스크립트로 위임하는 것이었다. 우리 팀의 게임은 낡고 더러운 방을 정리하는 1인칭 청소/분류 게임이다. 플레이어는 방 안의 오염을 청소하고, 발견한 물건을 보관 상자 또는 버릴 상자에 분류한다. 보관한 물건의 성격, 청소 진행도, 남은 시간, 완료한 미션에 따라 점수와 엔딩이 결정된다. 즉, C++ 엔진 코어는 Actor, Component, 충돌, UI, 오디오, 데이터 로딩 같은 기반 기능을 제공하고, 각 사물의 반응과 게임 규칙은 Lua와 Game 폴더의 시스템이 담당하도록 역할을 나누었다.

Lua 통합은 Engine/Scripting의 FLuaScriptSystem과 ULuaScriptComponent를 중심으로 구현했다. 엔진은 LuaJIT와 sol2를 사용하며, Lua 5.1 호환 런타임을 연다. LuaScriptComponent는 Actor에 부착되는 컴포넌트로, BeginPlay 때 스크립트를 로드하고, Tick마다 Lua의 Tick(owner, deltaTime)을 호출하며, EndPlay에서 정리한다. 기본 스크립트는 Asset/Scripts/template.lua로 만들었고 BeginPlay, EndPlay, Tick, OnOverlap, OnEndOverlap, OnHit, OnInteract 같은 공통 이벤트 함수를 제공한다. 새 스크립트를 만들 때는 template.lua를 복사해서 Asset/Scripts 아래에 생성한다. 기본 경로는 Actor 이름을 기반으로 만들어지며, 별도 이름을 입력하면 해당 이름의 lua 파일을 생성할 수 있다. 또한 LuaScriptComponent는 파일의 last write time을 주기적으로 확인해 변경이 감지되면 ReloadScript를 호출하므로, 에디터에서 스크립트를 수정한 뒤 곧바로 Hot Reload가 가능하다. OpenScriptFile 기능은 연결된 .lua 파일을 외부 텍스트 편집기로 열어주는 편의 기능이다.

Lua에 노출한 API도 게임 로직 위임을 기준으로 구성했다. print와 Log는 디버깅 출력을 담당하고, FindActorByName, GetPlayerActor, RaycastCenter는 스크립트가 월드와 상호작용할 수 있게 한다. SetGameState와 GetGameState는 여러 Lua 스크립트가 공유하는 간단한 게임 상태 저장소로, 예를 들어 Player.lua와 Bucket.lua, Mop.lua가 "DirtLevel:mop" 값을 공유해 대걸레가 얼마나 더러워졌는지를 표현한다. RegisterItemActor, RegisterCleaningToolActor, GetCurrentCleaningToolId, PlaySound, SetInteractionHint, SetUIState 같은 바인딩은 Lua에서 게임 시스템과 UI를 호출할 수 있게 해준다. 이 덕분에 C++은 안전하고 반복적인 엔진 기능을 맡고, 개별 사물의 의미와 반응은 Lua 스크립트에 남길 수 있었다.

Coroutine은 Lua의 시간 기반 게임 흐름을 처리하기 위해 구현했다. Lua 표준 coroutine API는 그대로 사용할 수 있지만, 게임에서는 wait(seconds)가 엔진 Tick과 연결되어야 하므로 FLuaCoroutineScheduler를 별도로 만들었다. StartCoroutine(function)으로 코루틴을 등록하면 C++ 스케줄러가 즉시 한 번 실행하고, Lua에서 wait(1.0) 또는 yield(1.0)을 호출하면 해당 코루틴은 정해진 시간만큼 대기한다. 이후 LuaScriptSystem의 Tick에서 CoroutineScheduler.Tick(deltaTime)이 호출되어 시간이 지난 코루틴을 자동으로 재개한다. CreateCoroutine, ResumeCoroutine, CancelCoroutine도 제공해서 즉시 시작, 지연 시작, 취소를 모두 다룰 수 있다. template.lua의 예시처럼 BeginPlay에서 코루틴을 시작해 1초, 2초 뒤 순차적으로 로직을 실행할 수 있고, ending_test.lua처럼 엔딩 연출에서 대화가 끝날 때까지 wait(0.1)을 반복하는 흐름에도 사용할 수 있다.

Delegate는 "확실히 위임하라"라는 주제와 직접 연결되는 구조다. Engine/Core/Delegate.h에는 가변 인자 템플릿 기반의 TDelegate가 구현되어 있고, DECLARE_DELEGATE 매크로로 필요한 시그니처를 선언한다. Add는 일반 콜백을 등록하고, AddDynamic은 UObject 인스턴스와 멤버 함수를 묶어서 등록한다. Broadcast는 등록된 모든 핸들러를 호출하며, 호출 중 객체가 이미 파괴되었는지 IsUObjectAlive로 확인해 죽은 객체의 콜백을 정리한다. UPrimitiveComponent의 OnComponentBeginOverlap, OnComponentEndOverlap, OnComponentHit도 이 Delegate 구조를 사용한다. LuaScriptComponent는 자신이 붙은 Actor의 PrimitiveComponent들에 HandleBeginOverlap, HandleEndOverlap, HandleHit을 AddDynamic으로 등록한다. 따라서 충돌 시스템이 Overlap 또는 Hit을 감지하면 PrimitiveComponent의 Delegate가 브로드캐스트되고, LuaScriptComponent가 이를 받아 Lua의 OnOverlap, OnEndOverlap, OnHit 함수로 넘긴다. C++ 충돌 판정과 Lua 게임 규칙이 느슨하게 연결되는 구조다.

ShapeComponent는 실제 게임 상호작용의 물리적 기반이다. UShapeComponent는 메시를 직접 그리는 것이 아니라 Box, Sphere, Capsule, Cylinder 같은 충돌 형태의 공통 부모로 동작한다. UPrimitiveComponent에는 GenerateOverlapEvents와 BlockComponent 플래그, OverlapInfos와 BlockingInfos, 그리고 Hit/Overlap Delegate가 있다. UBoxComponent 등 구체 ShapeComponent는 자신의 CollisionType을 설정하고, 월드 AABB와 RaycastMesh를 구현한다. 게임 오브젝트는 StaticMesh로 보이는 외형과 ShapeComponent로 판정되는 충돌체를 함께 가지며, RigidBodyComponent와 결합하면 플레이어가 집거나 떨어뜨릴 수 있다. 즉, 눈에 보이는 사물은 메시가 담당하고, 실제 상호작용 판정은 ShapeComponent와 충돌 시스템이 담당한다.

Game 폴더의 게임 구현은 청소, 물건 분류, UI, 엔딩, 점수를 담당한다. GGameContext는 현재 청소 진행도, 들고 있는 오브젝트, 발견/보관/폐기한 아이템, 완료 미션을 저장하는 런타임 컨텍스트다. 또한 OnContextChanged, OnItemDispositionChanged, OnHeldObjectChanged, OnObjectPickedUp, OnObjectDropped 같은 Delegate를 제공해 UI나 다른 시스템이 상태 변화를 구독할 수 있다. FItemSystem은 Items.json에서 로드된 아이템 데이터를 바탕으로 아이템 발견, 보관, 폐기, 조사 상태를 처리한다. FCleaningToolSystem은 대걸레와 스펀지 같은 도구 데이터, 청소력, 청소 반경, 애니메이션/사운드 정보를 관리한다. FEndingSystem은 보관한 아이템들의 endingRole을 평가해 Bad, Good, Normal 엔딩을 결정한다.

실제 Lua 스크립트는 Actor별 게임 규칙을 담당한다. CleaningTool.lua와 Mop.lua는 청소 도구 Actor를 등록하고, Mop.lua는 GameState의 DirtLevel:mop 값을 읽어 도구가 더러워질수록 색을 어둡게 바꾼다. Player.lua는 화면 중앙 RaycastCenter로 오염 Decal을 찾고, 마우스 입력과 현재 청소 도구의 power/radius를 이용해 Decal을 PaintAtWorldPos로 지운다. 청소를 계속하면 도구의 DirtLevel이 올라가고, Bucket.lua는 플레이어가 물통 근처에서 R키를 누를 때 해당 DirtLevel을 0으로 되돌리고 물에 씻는 사운드를 재생한다. OldFairyTaleBook.lua, CrumpledPaper.lua 등 아이템 스크립트는 BeginPlay에서 자신을 RegisterItemActor로 등록한다. 이렇게 사물별 의미는 C++ 클래스가 아니라 작은 Lua 파일에 나뉘어 있어, 게임잼 중 규칙 수정과 테스트가 빠르게 가능했다.

게임의 시작, 끝, 재시작, 스코어도 구현되어 있다. GameUISystem은 StartMenu, Prologue, InGame, Ending 상태를 관리한다. 시작 버튼을 누르면 타이틀 전환 뒤 프롤로그 대화가 나오고, 대화가 끝나면 InGame으로 들어간다. 플레이 중 HUD에는 청소 진행도, 남은 시간, 아이템 수, 상호작용 힌트가 표시된다. Ending 상태에 진입하면 FEndingSystem의 결과에 따라 엔딩 타입이 정해지고, EndingPanel은 GoodEnding, NormalEnding, BadEnding 이미지를 보여준다. 점수는 청소 점수 5000점, 남은 시간 점수 3000점, 아이템 점수, 미션 보너스 점수를 합산하는 방식으로 계산되며, 저장 시 Saves/Scores.txt에 기록되고 타이틀의 스코어보드에서 확인할 수 있다. 재시작 또는 타이틀 복귀 시 ResetGameData와 GGameContext::Reset을 통해 진행도, 아이템 상태, 엔딩 타입, 점수 입력 상태가 초기화된다.

정리하면 이번 구현은 발제 요구사항을 "엔진은 실행과 연결을 맡고, 게임 규칙은 Lua와 Delegate로 위임한다"는 방향으로 풀었다. LuaJIT 통합으로 Actor별 스크립트를 실행하고 Hot Reload할 수 있게 했으며, template.lua로 공통 이벤트 진입점을 통일했다. Delegate는 충돌 이벤트와 게임 상태 변경을 여러 시스템에 안전하게 전달하는 중심 통로가 되었고, Variadic Argument는 Delegate 템플릿과 Lua print/함수 호출 바인딩에서 다양한 인자 시그니처를 처리하는 데 사용되었다. Coroutine은 Tick 기반의 시간 흐름을 Lua에서 자연스럽게 작성하게 해주었다. ShapeComponent와 Overlap/Hit 이벤트는 실제 월드의 상호작용을 만들었고, Game 폴더의 청소/아이템/UI/엔딩 시스템은 이를 하나의 완성된 게임 루프로 묶었다.
