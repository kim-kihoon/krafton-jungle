# Understanding Focus and Force in 3D World

작성일: 2026-06-04

이 문서는 발표 주제인 **Understanding Focus and Force in 3D World**
(3차원 세상에서 초점과 힘의 이해)를 이 프로젝트의 렌더링/물리 시스템과 연결해서 설명한다.

핵심 주제는 이름이 비슷한 두 개의 DOF다.

- **Degrees of Freedom**: 물체가 3D 공간에서 움직일 수 있는 운동 자유도
- **Depth of Field**: 카메라가 초점을 맞춘 거리 주변만 선명하게 보이게 하는 피사계 심도

두 개념은 서로 다른 분야에 속하지만, 둘 다 3D 월드를 설계할 때 중요한 "제어 범위"를 다룬다. 물리 DOF는 물체가 어떤 방향으로 움직이고 회전할 수 있는지를 제한하고, 카메라 DOF는 화면에서 어떤 깊이 구간을 선명하게 보여줄지를 제한한다.

## 1. Degree of Freedom

### 개념

3D 강체(rigid body)는 기본적으로 6개의 자유도를 가진다.

| 분류 | 축 | 의미 |
| --- | --- | --- |
| 위치 이동 | X, Y, Z | 좌우, 전후, 상하 이동 |
| 회전 | Roll, Pitch, Yaw | X/Y/Z 축 기준 회전 |

즉, 물리 시뮬레이션에서 완전히 자유로운 강체는 다음 상태를 가진다.

```text
position = (x, y, z)
rotation = (roll, pitch, yaw)
linearVelocity = (vx, vy, vz)
angularVelocity = (wx, wy, wz)
```

이 프로젝트에서는 `UPrimitiveComponent`가 물리 API의 사용자 진입점이고, 실제 물리 바디는 `FBodyInstance`가 관리한다. PhysX 백엔드는 `FPhysXPhysicsScene`이 담당한다.

관련 파일:

- `KraftonEngine/Source/Engine/Component/PrimitiveComponent.h`
- `KraftonEngine/Source/Engine/Physics/BodyInstance.h`
- `KraftonEngine/Source/Engine/Physics/IPhysicsScene.h`
- `KraftonEngine/Source/Engine/Physics/PhysX/PhysXPhysicsScene.cpp`

### 힘과 토크

힘(force)은 선형 운동을 바꾸고, 토크(torque)는 회전 운동을 바꾼다.

```text
Force  -> linear acceleration  -> linear velocity  -> position
Torque -> angular acceleration -> angular velocity -> rotation
```

이 프로젝트의 public API는 다음처럼 분리되어 있다.

```cpp
void UPrimitiveComponent::AddForce(const FVector& Force);
void UPrimitiveComponent::AddForceAtLocation(const FVector& Force, const FVector& Location);
void UPrimitiveComponent::AddTorque(const FVector& Torque);
FVector UPrimitiveComponent::GetLinearVelocity() const;
FVector UPrimitiveComponent::GetAngularVelocity() const;
```

`AddForceAtLocation`은 단순히 물체를 밀기만 하는 것이 아니라, 힘이 질량 중심(center of mass)에서 벗어난 위치에 적용될 때 회전까지 만든다.

```text
torque = r x force
```

여기서 `r`은 질량 중심에서 힘이 작용한 지점까지의 벡터다. 예를 들어 자동차 차체의 한쪽 끝에 힘을 주면 차체가 앞으로만 움직이지 않고 회전하려는 성질도 생긴다.

### 고정 시간 간격과 안정성

프레임 시간은 매 프레임 달라질 수 있다. 물리 시뮬레이션을 가변 `DeltaTime`에 그대로 맡기면 충돌, 제약, 차량 주행이 프레임 레이트에 따라 다르게 보일 수 있다.

이 프로젝트의 PhysX 경로는 설정에 따라 fixed physics step을 사용한다.

```text
PhysicsAccumulator += DeltaTime
while PhysicsAccumulator >= FixedPhysicsStep:
    ApplyPendingForces()
    Scene->simulate(FixedPhysicsStep)
    Scene->fetchResults(true)
    PhysicsAccumulator -= FixedPhysicsStep
```

이 구조는 다음 장점이 있다.

- 프레임 레이트가 흔들려도 물리 결과가 더 안정적이다.
- 힘 적용 시점이 시뮬레이션 단계 앞에 모인다.
- 디버깅할 때 한 스텝 단위로 상태를 추적하기 쉽다.
- 네트워크 동기화나 리플레이 시스템으로 확장할 때 기반이 더 예측 가능하다.

단, 고정 스텝은 누적 시간이 너무 커질 때 substep 폭주를 막아야 한다. 현재 구현은 최대 substep 수와 누적 시간 clamp를 둔다. 이 정책은 유지보수 관점에서 중요하다. 물리가 늦어진 프레임을 무한히 따라잡으려 하면 게임 스레드가 더 늦어지는 악순환이 생길 수 있다.

### 자유도 제한

모든 물체가 6 DOF를 가져야 하는 것은 아니다.

예시:

- 캐릭터: 보통 Roll/Pitch 회전을 제한하고 Yaw 중심으로 회전한다.
- 문: 위치 이동은 막고 하나의 힌지 축 회전만 허용한다.
- 차량: 바퀴는 특정 축 회전과 조향 각도만 의미가 있다.
- 카메라 리그: 이동/회전 축 일부를 제한해 의도한 연출을 유지한다.

자유도 제한은 임시로 transform을 덮어쓰는 방식보다, 명시적인 constraint나 movement policy로 관리하는 편이 장기적으로 안전하다. transform을 여러 시스템이 직접 수정하면 물리, 애니메이션, 네트워크 보정, 에디터 조작이 서로 충돌하기 쉽다.

좋은 구조는 다음 책임을 분리한다.

| 책임 | 권장 위치 |
| --- | --- |
| 물리 바디 생성/해제 | `FBodyInstance` |
| 물리 월드 step/query | `IPhysicsScene` 구현체 |
| 컴포넌트 수준 API | `UPrimitiveComponent` |
| 캐릭터/차량의 의미 있는 제어 | 전용 movement component |
| 디버그 표시 | 별도 debug draw/debug info 경로 |

## 2. Depth of Field

### 개념

Depth of Field는 카메라가 초점을 맞춘 거리 주변은 선명하게, 그보다 앞이나 뒤에 있는 물체는 흐리게 표현하는 효과다.

카메라 관점에서 중요한 값은 다음과 같다.

| 값 | 의미 | 화면 영향 |
| --- | --- | --- |
| Focus Distance | 초점을 맞춘 월드 거리 | 해당 거리 근처가 선명해짐 |
| Focal Length | 렌즈 초점거리 | 화각과 배경 압축감에 영향 |
| F-Stop / Aperture | 조리개 값 | 낮을수록 흐림이 강해짐 |
| Sensor Size | 센서 크기 | 화각과 CoC 계산에 영향 |

F-Stop은 렌즈 초점거리와 조리개 지름의 비율이다.

```text
F-Stop N = focalLength / apertureDiameter
apertureDiameter = focalLength / N
```

따라서 F-Stop이 낮아지면 조리개 지름이 커지고, 초점 거리 밖의 물체가 더 크게 번진다. 예를 들어 `f/1.4`는 `f/8`보다 배경 흐림이 강하다.

### 이 프로젝트의 DOF 렌더링 흐름

현재 프로젝트는 카메라 설정에서 DOF 값을 가져와 포스트 프로세스 패스에 전달한다.

관련 파일:

- `KraftonEngine/Source/Engine/Component/Camera/CineCameraComponent.h`
- `KraftonEngine/Source/Editor/EditorRenderPipeline.cpp`
- `KraftonEngine/Source/Engine/Render/RenderPass/DOFSetupPass.cpp`
- `KraftonEngine/Source/Engine/Render/RenderPass/DOFGatherPass.cpp`
- `KraftonEngine/Source/Engine/Render/RenderPass/DOFRecombinePass.cpp`
- `KraftonEngine/Shaders/PostProcess/DOFSetup.hlsl`
- `KraftonEngine/Shaders/PostProcess/DOFGather.hlsl`
- `KraftonEngine/Shaders/PostProcess/DOFRecombine.hlsl`

렌더링 흐름은 다음과 같이 볼 수 있다.

```text
Scene Color + Scene Depth
        |
        v
DOFSetupPass
  - depth를 linear depth로 변환
  - focus distance와 비교
  - CoC(Circle of Confusion) 생성
        |
        v
DOFGatherPass
  - CoC 크기에 따라 주변 색 샘플링
  - blur texture 생성
        |
        v
DOFRecombinePass
  - 원본 scene color와 blur color를 CoC 기준으로 합성
```

`DOFSetup.hlsl`의 핵심은 깊이값으로부터 CoC를 계산하는 것이다.

```hlsl
float focalLengthMeters = FocalLength * 0.001f;
float apertureDiameter = focalLengthMeters / Aperture;
float imageDistance = focalLengthMeters * sceneDepth / (sceneDepth - focalLengthMeters);
float focusImageDistance = focalLengthMeters * FocusDistance / (FocusDistance - focalLengthMeters);
float cocOnSensor = apertureDiameter * ((imageDistance - focusImageDistance) / imageDistance);
float cocPixels = cocOnSensor * (ViewportHeight / SensorHeight);
```

CoC는 "이 픽셀이 초점에서 얼마나 벗어났는가"를 화면 픽셀 단위의 흐림 반지름으로 바꾼 값이다.

### Focal Length와 FOV

`EditorRenderPipeline.cpp`에서는 CineCamera가 활성화되어 있을 때 focal length로 FOV를 계산한다.

```cpp
const float SensorHeight = 24.0f;
RenderPOV.FOV = 2.0f * atanf((SensorHeight * 0.5f) / Frame.DepthOfFieldFocalLength);
```

초점거리가 길어질수록 FOV는 좁아지고, 화면은 망원 렌즈처럼 보인다. 반대로 초점거리가 짧아질수록 FOV는 넓어지고 광각 렌즈처럼 보인다.

주의할 점은 Depth of Field와 FOV가 서로 독립적인 값처럼 보이지만, 실제 렌즈 모델에서는 focal length가 둘 모두에 영향을 준다는 것이다. 따라서 카메라 시스템을 확장할 때는 DOF 파라미터와 FOV 파라미터가 서로 다른 곳에서 중복 계산되지 않도록 데이터 흐름을 명확히 유지해야 한다.

## 3. 두 DOF의 공통점

두 DOF는 모두 "현실의 연속적인 3D 현상"을 엔진에서 제어 가능한 파라미터로 모델링한다.

| 항목 | Degrees of Freedom | Depth of Field |
| --- | --- | --- |
| 분야 | 물리/운동 | 렌더링/카메라 |
| 제어 대상 | 물체의 이동과 회전 | 화면의 선명도와 흐림 |
| 핵심 입력 | force, torque, mass, constraint | focus distance, focal length, aperture |
| 안정성 이슈 | timestep, collision, constraint drift | depth precision, blur cost, edge artifacts |
| 디버깅 방법 | velocity, COM, collision shape 시각화 | depth, CoC, focus plane 시각화 |

둘 다 단순히 "효과가 보이게" 만드는 것보다 데이터 흐름과 디버그 가능성이 중요하다.

물리에서는 어떤 시스템이 force를 넣었는지, 어느 step에서 적용되었는지 추적할 수 있어야 한다. DOF에서는 어떤 카메라가 focus distance를 정했는지, 어떤 depth가 CoC로 변환되었는지 볼 수 있어야 한다.

## 4. 발표 데모 제안

### Rigid Body Simulation 데모

보여줄 내용:

- 큐브 또는 차량 차체에 `AddForce` 적용
- 같은 힘을 중심에 적용했을 때와 한쪽 모서리에 적용했을 때 비교
- `AddTorque`로 직접 회전시키는 경우 비교
- mass와 center of mass를 바꿨을 때 안정성 변화 확인

설명 포인트:

- 중심에 힘을 주면 선형 운동이 주로 발생한다.
- 중심에서 벗어난 위치에 힘을 주면 회전 운동도 생긴다.
- 3D 강체는 6 DOF를 가지지만, 게임 오브젝트는 설계 의도에 따라 일부 자유도를 제한해야 한다.
- fixed timestep은 프레임 레이트와 물리 안정성을 분리하기 위한 핵심 구조다.

### Depth of Field 데모

보여줄 내용:

- 가까운 오브젝트, 중간 오브젝트, 먼 오브젝트를 일렬로 배치
- focus distance를 가까운 물체에서 먼 물체로 이동
- F-Stop을 낮게/높게 바꿔 흐림 강도 비교
- focal length를 바꿔 FOV와 배경 압축감 비교

설명 포인트:

- 초점 거리 근처의 물체만 선명하게 보인다.
- F-Stop이 낮을수록 피사계 심도가 얕아진다.
- 이 프로젝트는 depth buffer를 읽어 CoC를 만든 뒤 gather blur와 recombine으로 DOF를 합성한다.
- DOF는 시각 효과지만, depth precision과 post-process 비용 때문에 성능/품질 균형이 필요하다.

## 5. 유지보수 관점의 체크리스트

물리 시스템:

- force/torque 적용은 물리 step 직전에 모아서 처리한다.
- transform 직접 덮어쓰기와 dynamic simulation이 충돌하지 않게 정책을 분리한다.
- constraint, movement component, vehicle system은 물리 scene 내부 구현에 과하게 의존하지 않게 한다.
- collision shape, center of mass, velocity를 디버그 표시할 수 있어야 한다.
- 네트워크나 리플레이 확장을 고려하면 fixed step과 입력 기록 단위를 명확히 해야 한다.

DOF 시스템:

- 카메라 파라미터의 소유자를 명확히 한다.
- focal length, aperture, focus distance의 단위를 일관되게 관리한다.
- depth linearization과 near/far clip 값이 렌더 파이프라인 전체에서 같은 규칙을 써야 한다.
- CoC texture를 디버그 뷰로 확인할 수 있어야 한다.
- blur kernel 크기와 샘플 수는 성능 예산 안에서 제어해야 한다.

## 6. 요약

Degrees of Freedom은 3D 월드에서 물체가 어떻게 움직일 수 있는지를 설명하고, Depth of Field는 3D 월드를 카메라가 어떻게 초점과 흐림으로 표현하는지를 설명한다.

이 프로젝트에서는 물리 쪽은 `UPrimitiveComponent -> FBodyInstance -> IPhysicsScene/FPhysXPhysicsScene` 구조로, 카메라 DOF는 `CineCameraComponent -> FrameContext -> DOF post-process passes` 구조로 연결된다.

두 시스템 모두 장기적으로 유지하려면 파라미터의 소유권, 업데이트 순서, 디버그 시각화, 성능 예산을 명확히 해야 한다. 이것이 단순한 데모 효과와 실제 게임 엔진 기능의 차이다.
